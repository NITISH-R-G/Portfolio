# Portfolios for machines

A portfolio built with this engine is two things at once: a page a person reads, and a
structured document a program reads. This describes the second one — what is published, how to
find it, what may be relied on, and where the privacy line sits.

Nothing here is specific to one portfolio. Any site built on this engine exposes the same
interface, which is the point: a tool written against one conforming portfolio works against
all of them.

---

## The manifest

Every build emits a machine-readable manifest beside `index.html`:

```
https://example.com/portfolio.json
https://user.github.io/repo/portfolio.json      # project sites, mounted under /repo/
```

It is a [Portfolio Standard](standard.md) document — the same versioned format `npm run
export` produces — carrying the person, their collections, their socials, and the provenance
of what it publishes.

```json
{
  "schemaVersion": "1.0",
  "spec": "https://github.com/NITISH-R-G/Portfolio/blob/main/docs/standard.md",
  "url": "https://example.com/",
  "person": { "name": "…", "headline": "…", "summary": "…" },
  "projects": [ … ], "experience": [ … ], "skills": [ … ],
  "socials": { "github": "…" },
  "capabilities": { "schemaVersion": "1.0", "provenance": true, "evidence": true, "search": "client" }
}
```

`capabilities` is there so a consumer can branch on what a portfolio supports instead of
probing for fields and inferring from their absence.

### Turning it off

```js
// portfolio.config.js
export default defineConfig({
  agent: { manifest: false },
})
```

The manifest is emitted even when `seo.sitemap` is disabled. Those settings govern how *search
engines* treat the page; the manifest is for tools reading a portfolio someone handed them
directly, and switching off sitemaps was never a request to be unreadable by software.

## Discovery

The authoritative pointer is a link in the document head:

```html
<link rel="alternate" type="application/portfolio+json" href="./portfolio.json" title="Portfolio manifest">
```

This is the same autodiscovery mechanism feed readers have used since 2002 — hand a tool any
page URL and it finds the machine-readable version. It keeps working if a portfolio is mounted
somewhere unusual, or serves its manifest from another host entirely.

A consumer should read the link first and fall back to convention (`portfolio.json` beside the
page, then at the origin root) only when the page declares nothing.

### Why not `/.well-known/portfolio.json`

RFC 8615 defines `.well-known` relative to the **origin root**. The default deployment target
here is a GitHub Pages *project* site at `https://user.github.io/repo/`, where the origin root
belongs to the user's account rather than the repository — a project site physically cannot
serve `/.well-known/…`. Adopting it would have broken discovery for the most common way this
engine is deployed. A base-relative manifest plus an explicit link tag works everywhere,
including at a domain root where `.well-known` would also have been available.

### Also published

| File | What it is |
| --- | --- |
| `portfolio.json` | The manifest |
| `sitemap.xml` | Standard sitemap |
| `robots.txt` | Standard robots directives |
| JSON-LD in `<head>` | schema.org `Person`, `ProfilePage`, `WebSite`, `ScholarlyArticle` |

JSON-LD and the manifest serve different readers and are both worth having: search engines
understand schema.org, while the manifest carries provenance, evidence and full collections
that schema.org has no vocabulary for.

## Privacy boundary

**The manifest is a security boundary, not a data dump.** It is generated by
`core/standard/public.js`, which is separate from the serializer used for local exports
precisely so that publishing rules cannot be bypassed by accident.

| Rule | Behaviour |
| --- | --- |
| `identity.contact.phone` | **Never published.** No configuration re-enables it. |
| `privacy.hideEmail: true` | Email omitted. |
| `privacy.obfuscateEmail: true` *(default)* | Email omitted. |
| Disputed-claim evidence | Not published. |
| Per-record `source` | Published — it describes a value that *was* published. |
| Skill `evidence` | Published. |

Three of those deserve their reasoning stated:

**Phone is absolute.** No connector can import a phone number, so its presence in a config
means a human typed it for their own page. That is consent to render it, not consent to publish
it as a bulk-collectable record. A configuration flag would eventually be set by someone who
had not thought it through.

**Obfuscation means omission.** `obfuscateEmail` renders `name [at] example.com` on the page to
frustrate naive scrapers. Emitting that same string into JSON would be worse than useless —
unusable by a legitimate agent, and still an advertisement that an address exists. Emitting the
*real* address would defeat the setting entirely. So the field is dropped.

**Losing claims stay private.** The standard can carry the full evidence graph, including every
claim on a contested value. If someone imported a private résumé and corrected a job title, the
losing claim is that résumé's original wording. Publishing it would leak private document
content. Provenance for values that *were* published travels on the records themselves.

## Reading a portfolio in code

```bash
npm install @portfolio-engine/agent
```

```js
import { PortfolioAgent } from '@portfolio-engine/agent'

const portfolio = await PortfolioAgent.fromUrl('https://example.com/portfolio/')

portfolio.person
portfolio.getProjects()
portfolio.search('projects involving computer vision')
portfolio.findSkill('Python')        // the skill and what demonstrates it
portfolio.toMarkdown()
portfolio.toPrompt()
```

Full API: [`packages/agent/README.md`](../packages/agent/README.md).

The package never scrapes rendered UI. It fetches HTML for exactly one purpose — reading the
discovery link — and never for profile data, so it survives a complete visual redesign.

### Search

Deterministic, offline and requires no API key. Lexical retrieval (saturating term frequency,
inverse document frequency, field and collection weighting) plus a small curated concept
vocabulary that maps query words onto the words portfolios actually use, which is what lets
*"computer vision"* reach work described as *"object detection"*.

It is **not** embeddings, and the capability reports `"lexical"` rather than `"semantic"` so no
consumer is misled. A curated vocabulary handles what it covers well and what it does not cover
not at all; embeddings degrade gracefully across everything. An embeddings tier can be added
without changing the interface.

Every result explains itself — which terms matched, in which field, whether they were typed or
expanded, and what backs the record:

```js
{
  title: 'abyssal-nav',
  score: 47.7,
  matched: [
    { term: 'navigation', field: 'text', direct: true },
    { term: 'slam', field: 'tags', direct: false }   // ← concept expansion
  ],
  provenance: { source: 'github', evidence: [{ label: '18 repositories', count: 18 }] }
}
```

### Model-backed questions

```js
await portfolio.ask('What demonstrates backend work?', {
  complete: async (prompt) => callYourModel(prompt),
})
```

No default provider, no bundled key, no hosted endpoint. You supply a function that talks to a
model you already pay for; the package builds the grounded prompt and returns deterministic
grounding alongside the answer so sources can be shown rather than trusted.

## Copy as Markdown / Copy as Prompt

Every profile and entity on the page can be copied as clean Markdown, or as a prompt with
grounding instructions attached:

> Use only the information in this profile. If the profile does not support an answer, say so
> plainly rather than inferring one. Where a claim has evidence attached, cite it. Listing a
> technology on a project is not a claim about years of experience.

Those instructions matter more than the data. A model handed a CV and no instructions answers
questions the CV never addressed, about a real person who has to live with the answer.

Both are produced by the same functions the npm package exports, through the same privacy
boundary as the published manifest — so what a person copies can never contain something the
manifest withholds.

## Compatibility

`schemaVersion` is `major.minor`. A consumer should:

- **accept** an unknown *minor* version and ignore fields it does not recognise;
- **refuse** an unknown *major* version rather than guess — silently misreading a shape you do
  not understand produces confidently wrong answers about a real person;
- **preserve** unknown fields when round-tripping, so a portfolio carrying something this
  version does not model survives the trip.
